# HyperSCA 通俗术语与表达规范设计

日期：2026-08-12  
状态：已确认，待实施

## 1. 目标

HyperSCA 面向生物医学研究者、临床与实验人员以及计算研究者。当前项目包含较多软件工程和机器学习习惯用语，容易让读者先理解工具形式，才能理解研究目的。本次调整建立统一的双层表达方式：正文先说明研究含义，标准术语只在首次出现时放在括号中，供专业检索、论文写作和跨团队沟通使用。

调整后的文字应使非计算背景的读者能够回答三个问题：这一步研究什么、为什么需要它、结果能说明到什么程度。表达变得通俗不能改变统计定义、因果边界或证据等级。

## 2. 已确认的读者与范围

采用混合读者方案：

- 面向临床、实验和生物医学读者的正文使用通俗中文。
- 首次出现时保留标准英文或专业术语，例如“未参与模型建立的独立验证数据（holdout）”。
- 后续可在不会造成歧义时只使用通俗名称。

本次修改用户可见的文字，不改动下列稳定接口：

- Python 函数、类和模块名称；
- 命令行参数名；
- JSON、CSV 和其他分析输出中的字段名；
- 已发布版本中的文件名和目录结构；
- 文献标题、引用原文和第三方工具的正式名称。

如果稳定接口本身含有计算机术语，应在附近的帮助文字或文档中解释，不通过重命名破坏兼容性。

## 3. 表达原则

### 3.1 先讲研究含义

段落和列表项先说明生物学、统计学或工作流程含义，再给实现名称。避免用工具结构代替研究解释。

推荐：

> 因果稳定性检查会重复抽样，观察同一条关系是否反复出现。结果作为独立的补充分析（sidecar）保存，不改变候选靶点排序。

不推荐：

> Causal sidecar 生成 bootstrap artifact，不进入 ranking pipeline。

### 3.2 标准术语首次括注

第一次出现时采用“通俗名称（标准术语）”。代码、命令、字段名放在反引号中，并说明其含义。一个短段落内不重复给出同一英文术语。

### 3.3 保留科学准确性

以下概念不做模糊替换，但需要简短解释：因果效应、反事实、置信区间、校准、空间混杂、负控、外部验证、可识别性和多重检验。不得把“相关”改写成“因果”，不得把“候选”改写成“有效靶点”，不得把计算模拟写成实验验证。

### 3.4 用证据状态代替工程状态

用户可见文字优先描述证据处于什么阶段。例如将“promotion failed”表达为“尚未达到进入下一证据阶段的条件”，同时在括号或字段说明中保留 `promotion_status`。

### 3.5 一句话只承担一个主要信息

减少由多个英文缩写、斜杠和括号串联的长句。必要时拆成“用途—做法—限制”三句。首次使用缩写时给出全称或中文解释。

## 4. 核心术语表

| 标准术语或现有名称 | 用户可见的首选表达 | 必须补充的含义 |
|---|---|---|
| pipeline | 分析流程 | 数据依次经过哪些研究步骤 |
| workflow | 工作流程 | 谁在什么顺序执行哪些步骤 |
| benchmark | 对照评估 | 在相同条件下比较方法 |
| benchmark contract | 预先固定的比较规则 | 提前确定数据、指标和通过条件 |
| baseline | 简单对照方法 | 用来判断复杂方法是否真的带来增益 |
| holdout | 未参与模型建立的独立验证数据 | 不用于选特征或调参数 |
| artifact | 分析输出文件 | 可复查的表格、图或记录文件 |
| manifest | 分析记录清单 | 记录输入、版本、参数和输出位置 |
| sidecar | 独立的补充分析 | 提供旁证，但不改变主结果 |
| adapter | 数据或方法接入层 | 把外部格式转成项目可读取的形式 |
| promotion gate | 进入下一证据阶段的条件 | 达标才允许提高结论等级 |
| evidence-gated ranking | 由直接证据决定的排序 | 补充模型不能越过直接证据改名次 |
| coverage | 可作出判断的比例 | 有足够信息并给出结果的对象占比 |
| abstention | 暂不判断 | 信息不足时明确不作预测或结论 |
| null control | 零效应对照或负控 | 检查随机关系是否也会产生类似结果 |
| bootstrap | 重复抽样检查 | 通过多次抽样评估结果稳定性 |
| split | 数据划分 | 哪些数据用于建立、调整和验证方法 |
| tuning budget | 参数尝试上限 | 各方法允许尝试的设置次数相同 |
| smoke test | 最小运行检查 | 只证明流程能运行，不证明科学有效 |
| fail closed | 条件不全时停止并判为未通过 | 不用默认值掩盖缺失证据 |
| CLI | 命令行使用方式 | 通过终端运行脚本的方法 |
| schema | 数据字段规范 | 必须包含哪些字段及其含义 |
| digest / hash | 文件内容指纹 | 用于确认输入文件没有被悄悄替换 |

该表是首选表达清单，不是机械替换表。改写时必须结合上下文，避免把第三方正式名称或统计定义替换错误。

## 5. 实施组成

### 5.1 长期项目规则

在仓库根目录新增或纳入版本管理的 `AGENTS.md` 中设置“面向读者的语言规范”。规则适用于以后新增或修改的 README、研究文档、命令行帮助、错误信息、运行摘要和图注。贡献者在修改用户可见文字时应查阅项目术语指南。

### 5.2 项目术语指南

新增 `docs/style/plain_language_terminology.md`，收录本设计中的原则、术语表、正反例和科学边界。`AGENTS.md` 保留简明的强制规则，并链接到完整指南，避免长期规则过长。

### 5.3 当前高频入口改写

第一轮覆盖仍在维护且最常被阅读的入口：

1. 根目录 `README.md`；
2. `docs/research/` 中当前有效的排名、负控、C/S/D 比较规则与简单对照方法说明；
3. `scripts/` 中面向用户的 `argparse` 描述、参数帮助、错误提示和运行摘要；
4. 与这些入口直接对应的测试断言。

历史报告、已发布 release note 和 Bear 检索原始记录不做整篇改写。需要从当前入口链接它们时，在链接文字附近补充通俗说明。这样既改善入口体验，也保留当时的研究记录。

### 5.4 后续增量约束

新增一个轻量文档检查，扫描当前维护范围内高频计算机术语。检查不禁止标准术语，而是要求它们满足下列任一条件：

- 位于代码片段、命令、文件路径或字段名中；
- 在同一段首次出现时已有中文解释；
- 位于允许保留的第三方正式名称或引用中；
- 通过集中维护的例外清单给出理由。

检查只约束新增和当前维护的入口，不对历史报告进行大规模追溯报错。

## 6. 改写流程

每个用户可见段落按以下顺序处理：

1. 找出读者真正需要理解的研究问题或操作结果。
2. 将实现结构改写为研究动作，例如把“生成 artifact”改为“保存可复查的分析输出文件”。
3. 在首次出现处括注标准术语、命令或字段名。
4. 检查科学边界，确认没有把关联、预测、模拟或旁证升级为验证结论。
5. 检查兼容性，确认没有更改代码标识符、参数或输出字段。
6. 运行术语检查、相关文档测试和完整测试。

## 7. 错误信息与命令行帮助

错误提示采用“发生了什么—为什么不能继续—用户该做什么”的结构。例如：

> 独立验证数据缺少 `spatial_block` 字段，因此无法确认训练区域与验证区域是否分开。请按数据字段规范补充该列后重新运行。

不得只返回“schema invalid”或“attestation failed”。底层异常名称可保留在末尾，供排错使用。

命令行参数名保持不变，但 `help` 应解释研究含义、预期单位、默认行为以及会不会影响主要结论。

## 8. 验证方法

实施完成后至少进行以下验证：

- 对术语指南和长期规则进行存在性与内容测试；
- 对维护范围执行高频术语检查，确认未解释用法为零；
- 对修改过的 CLI 执行 `--help` 检查；
- 运行相关定向测试；
- 运行 `pytest tests -q -p no:cacheprovider`；
- 运行 `git diff --check`；
- 人工抽查 README、一个因果文档、一个空间文档和一个错误提示，确认通俗表达没有改变科学结论。

## 9. 验收条件

完成状态必须同时满足：

1. 根目录 `AGENTS.md` 已纳入版本管理并包含长期语言规则。
2. 完整术语指南可从 README 和 `AGENTS.md` 找到。
3. README 和当前 C/S/D、排名、负控说明采用双层表达。
4. 本轮涉及的 CLI 帮助与错误提示能直接告诉非计算读者如何处理问题。
5. 稳定代码接口、命令参数和输出字段没有重命名。
6. 历史报告和文献原文没有被机械覆盖。
7. 自动检查和完整测试通过。
8. 改写没有提升任何算法、药物或因果结论的证据等级。

## 10. 非目标

本次不承担以下工作：

- 翻译全部第三方论文标题和软件名称；
- 重命名源码中的类、函数、参数和字段；
- 为所有历史报告重新排版或重写；
- 用口语替代数学定义；
- 改变算法、评价指标、数据划分或进入下一证据阶段的条件。
