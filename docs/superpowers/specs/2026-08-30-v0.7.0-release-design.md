# HyperSCA v0.7.0 Release Design

## Goal

Publish the completed Methods v3 work as HyperSCA `v0.7.0` through the protected
`main` branch without force-pushing or introducing merge commits. The release
must make the scientific evidence boundary visible: the Methods v3 bridge is
implemented and audited, while a real external spatial-perturbation pilot remains
blocked when the registered cohort is unavailable.

## Linear release history

Create `release/v0.7.0` from the latest `origin/main`. Reproduce the final tree of
local commit `eb2b621141657334b1f098726b72d40bf1891b26` as one linear snapshot
commit, then add the release documentation and image as a second linear commit.
The resulting branch must contain no merge commits relative to `origin/main`, and
its pre-release snapshot tree must exactly match `eb2b621`.

The existing remote branch `run/public-pilot-v22-20260828` remains an audit copy
of the detailed development history. It is not the branch submitted to the
protected `main` branch.

## Version and reader-facing documentation

- Change the package version in `pyproject.toml` from `0.6.1.dev0` to `0.7.0`.
- Add `docs/releases/v0.7.0.md` with a concise feature summary, verification
  evidence, compatibility notes, and the external-cohort stop condition.
- Keep `README.md` as the complete Chinese landing page and add `README_EN.md` as
  the complete English landing page.
- Put a visible `中文 | English` language switch at the top of both files. Each
  language label links to the corresponding repository document.
- Give both README files the same section order, release facts, scientific claims,
  caveats, commands, and links. Translation may be idiomatic, but neither language
  may add or omit a scientific conclusion or promotion claim.
- Update both README release sections from `v0.6.0` to `v0.7.0`.
- Explain Methods v3 in plain language: frozen comparison contracts, whole-animal
  spatial splits, evidence-gated scoring/publication, and architecture controls.
- State explicitly that unavailable external data produces a stop-gate record,
  not a fabricated pilot result or promotion claim.

## Validation and protected-branch publication

Before publication:

1. Confirm the release branch is linear and contains no merge commits after
   `origin/main`.
2. Confirm the imported snapshot tree matches `eb2b621` before release-only edits.
3. Run the local equivalents of the `core-python-310` workflow:
   - install/use the Python 3.10 core environment already available in the repo;
   - `python scripts/validate_env.py --profile core-cpu`;
   - `python scripts/check_plain_language.py`;
   - the repository test suite, avoiding redundant reruns unless files change.
4. Validate both README language-switch links, section parity, image references,
   image presence, package version, and `git diff --check`.

Push `release/v0.7.0`, open a pull request against `main`, and wait for the required
`core-python-310` status. Merge without creating a merge commit. Only after the
protected `main` contains the release commit, create and push the annotated
`v0.7.0` tag. Do not force-push and do not modify the dirty archive checkout.

## Failure handling

- If the snapshot tree differs from `eb2b621`, stop before committing.
- If image text or scientific flow is materially incorrect, regenerate once with
  a targeted prompt correction before embedding it.
- If local validation or GitHub CI fails, fix the release branch and rerun only
  the affected checks plus the final required gate.
- If branch protection prevents automated merge or tag publication after CI is
  green, leave the verified PR open and report the exact unmet rule.
